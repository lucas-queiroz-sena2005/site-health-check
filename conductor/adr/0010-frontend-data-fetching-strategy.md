# Frontend Data Fetching Strategy & The Impossible Triangle

## Context

The React frontend must render deeply hierarchical data (`CIDR -> IP -> Port -> TLS/HTTP`) generated by network scans. A critical challenge arises when scanning large ranges (e.g., a `/16` CIDR block containing 65,536 IPs). The architectural decision centers on how the frontend fetches, filters, and renders this massive dataset without crashing the browser or DDoS'ing the backend.

During the design phase, we evaluated the "Impossible Triangle" of hierarchical data fetching:

1. **Hydrate All (Coarse-Grained):** The API returns the entire nested JSON tree in one request.
   - *Pros:* UI is instantaneous. Global "bottom-up" filtering (e.g., searching for leaf-node expired certificates) is trivial because the frontend has all data in RAM.
   - *Cons:* Payload size can easily exceed 100MB on a `/16` scan, crashing the browser.
2. **Lazy Loading / DataLoader (Fine-Grained):** The UI only loads Root nodes. Expanding a node triggers a batched API request (DataLoader) for its children.
   - *Pros:* Solves the 100MB payload problem. Components are perfectly decoupled.
   - *Cons:* Makes global "bottom-up" filtering mathematically impossible (the frontend cannot filter by a child property if the child hasn't been lazy-loaded yet).
3. **Query DSL / GraphQL / Sparse Trees:** The frontend sends a complex JSON "Recipe" or GraphQL query specifying exactly what filters to apply at every nested layer, and the backend returns a pre-filtered "Sparse Tree".
   - *Pros:* Solves both payload size and global filtering.
   - *Cons:* Introduces massive backend complexity (dynamic SQLAlchemy JOINs, GraphQL DataLoaders to prevent N+1 queries) and adds network latency to every UI click.

## Decision

1. **Adopt "Hydrate All" as the standard frontend fetching pattern.**
2. **Discard "Auto-Classification" / Tag Grouping for the MVP.**

## Rationale

### Why "Hydrate All" works (Void Aggregation)
We chose to reject GraphQL, `fastapi-filter`, and Frontend DataLoaders because the primary weakness of "Hydrate All" (massive payload sizes) is already solved by the backend's existing `aggregate_void_nodes` function (ADR 0004). 

Because the backend artificially squashes thousands of unresponsive/empty IPs into a single string (e.g., `"Void (65,436)"`), a `/16` scan of a sparse cloud network will yield a very small JSON payload. The frontend can safely cache this entire payload using TanStack Query, enabling instantaneous UI interactions and trivial in-memory JavaScript filtering.

### Why Classifications were discarded
We evaluated dynamically grouping IPs by heuristic tags (e.g., scanning TLS certificates to group IPs into a `databases` tier). This was discarded for the MVP to strictly simplify the hierarchy to `CIDR -> IP -> Port`. 

By removing dynamic classifications, we guarantee a deterministic tree structure, allowing the React components to remain purely "dumb" presentation layers that map over the data passed down as props from the TanStack Query cache.

## Rejected Alternatives

- **GraphQL / fastapi-filter:** Rejected due to implementation complexity. GraphQL natively suffers from the N+1 problem, requiring complex DataLoaders on the backend. It shifts state management to the server, meaning every UI interaction requires a network round-trip.
- **Frontend DataLoader:** Rejected because it permanently prevents the user from executing global searches on leaf-node data (e.g., "Show me all expired certificates across this /16 block") without switching to a completely different "Flat Table" UI mode.

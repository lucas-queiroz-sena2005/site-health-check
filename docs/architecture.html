System Overview

How the Site Health Check system is structured, what each piece does, and how they connect.

Terminology

Job

A user-facing scan request. Could be a single domain, a CIDR block, or a category name like "professors". Created by the Frontend or CLI. Stored in SQLite.

TaskConfig

The standardized JSON payload the Engine accepts. Contains a single target string, a list of ports, and a TaskFlags object. This is what exists in the code today.

IpState (Result)

The Engine's output. A nested dict keyed by IP address, containing port states, TLS certificates, HTTP routing checks, and metadata. This is the current output format.

Labels (Future)

Key-value metadata tags (e.g., group: students). Not yet implemented. Will enable Prometheus-style querying and Frontend filtering.

Existing Data Models

All models are Python dataclasses in src/site_health_check/schemas/.

Input Models (what the Engine receives)

TaskConfig

target: str              # "susy.ic.unicamp.br"
ports: list[int]         # [80, 443, 8443]
flags: TaskFlags         # see below
discovered_from: str?    # SAN recursion parent

TaskFlags (12 fields)

check_tcp: bool = True
check_http: bool = True
timeout_seconds: int = 10
expected_strings: list[str]? = None
undesired_strings: list[str]? = None
recursive_san_check: bool = False
check_virtual_hosts: bool = True
out_of_scope_depth: int = 0
spoof_user_agent: bool = False
worker_delay: float = 0.0

Output Models (what the Engine produces)

IpState (root per IP)

metadata: dict[str, str]
  # e.g. {"resolved_from": "susy..."}
ports: dict[int, PortState]
  # e.g. {443: PortState(...)}

PortState (per port)

tcp_status: str       # "open" / "closed"
tcp_latency_ms: int?
tls_certificate: TlsCertificate?
http_routing_checks: 
  dict[str, HttpRoutingCheck]
  # domain → HTTP result

TlsCertificate

valid: bool
expires_in_days: int
issuer: str?
domains_discovered_sans: list[str]

HttpRoutingCheck

status_code: int?
path_checked: str = "/"
notes: str?

What Does NOT Exist Yet

No Database

Zero persistence. Results go to stdout or a JSON file dump.

No API / Frontend

CLI-only via argparse. No FastAPI, no React, no HTTP endpoints.

No Message Queue

No RabbitMQ. Internal asyncio.Queue only (in-process, not distributed).

Module Map & Responsibilities

What each module does, what it must never do, and which language it is written in.

Frontend (React)

AspectDetails
LanguageTypeScript / React
Talks toAPI only (via REST HTTP)
DoesDisplay scan results dashboard. Provide forms for creating Jobs (target input, port selection, flag toggles). Show scan progress and history. Allow browsing results by Job, by IP, by domain.
Does NOTNever sends raw CIDR blocks to be expanded. Never talks to RabbitMQ or SQLite directly. Never runs scan logic.

API (FastAPI)

AspectDetails
LanguagePython (FastAPI)
Talks toFrontend (serves HTTP), SQLite (reads/writes), Dispatcher (triggers)
DoesAccepts Job creation requests from Frontend. Validates input. Saves Job definition + flags to SQLite. Returns job_id. Serves paginated results from SQLite to Frontend. Handles future auth.
Does NOTNever expands CIDR blocks. Never pings websites. Never talks to RabbitMQ directly.

Dispatcher (Splitter)

AspectDetails
LanguagePython (stays Python permanently)
Talks toAPI (receives Job), SQLite (looks up categories), RabbitMQ (publishes Tasks)
DoesReads a Job from the API. Expands CIDR ranges, IP ranges, and category lookups into individual targets. Uses existing parsing.py logic. Builds TaskConfig.to_dict() payloads. Streams them one-by-one into RabbitMQ's Task queue.
Does NOTNever pings websites. Never serves web traffic. Never writes scan results.
Key: The Dispatcher reuses the existing parsing.py and expand_target_ranges() code. That logic simply moves out of cli.py and into the Dispatcher module.

Scanner (Execution Engine)

AspectDetails
LanguagePython (MVP) → Go (Production)
Talks toRabbitMQ (pulls Tasks, pushes Results), Target websites (TCP/TLS/HTTP probes)
DoesPulls a TaskConfig from RabbitMQ. Runs engine.py logic: DNS resolution, TCP connect, TLS cert extraction, HTTP routing checks, SAN recursive discovery (internal BFS). Returns the full IpState result to RabbitMQ Results queue.
Does NOTNever talks to SQLite. Never expands CIDR blocks. Never serves HTTP endpoints. Has zero knowledge of "Jobs" or "categories".
SAN Recursion stays here. The internal BFS loop and asyncio.Queue that discovers SANs and re-queues them stays inside the Scanner for the MVP. This means recursion is self-contained within one Scanner instance.

Result Writer

AspectDetails
LanguagePython
Talks toRabbitMQ Results queue (consumes), SQLite (writes)
DoesConsumes finished IpState results from the Results queue. Deserializes the JSON. Writes structured rows into SQLite tables. Later: a second consumer writes to Prometheus.
Does NOTNever pings websites. Never talks to the Frontend. Never expands jobs.

Data Contracts

The exact JSON shapes flowing between each module. These are the "seams" that allow us to swap Python for Go later.

Contract 1: Frontend → API (Job Creation)

What the React frontend sends when a user requests a scan.

POST /api/jobs

{
  "target": "192.168.1.0/24,susy.ic.unicamp.br",
  "ports": "80,443",
  "flags": {
    "check_tcp": true,
    "check_http": true,
    "timeout_seconds": 10,
    "recursive_san_check": true,
    "out_of_scope_depth": 1,
    "expected_strings": ["login"],
    "check_virtual_hosts": true,
    "spoof_user_agent": false
  },
  "labels": {
    "target_group": "professors"
  }
}

Response: { "job_id": "JOB-0042", "status": "dispatching" }
The flags object maps directly to the existing TaskFlags dataclass. The target string uses the same flexible format the CLI already supports (CIDR, ranges, domains, comma-separated).

Contract 2: Dispatcher → RabbitMQ (Task Queue)

What the Dispatcher publishes after expanding the Job. This is the existing TaskConfig.to_dict() format, plus job_id and labels.

// One message per expanded target. A /24 CIDR = 254 of these messages.
{
  "job_id": "JOB-0042",
  "target": "192.168.1.5",
  "ports": [80, 443],
  "flags": {
    "check_tcp": true,
    "check_http": true,
    "timeout_seconds": 10,
    "recursive_san_check": true,
    "out_of_scope_depth": 1,
    "expected_strings": ["login"],
    "undesired_strings": null,
    "check_virtual_hosts": true,
    "spoof_user_agent": false,
    "worker_delay": 0.0
  },
  "discovered_from": null,
  "labels": {
    "target_group": "professors"
  }
}
The Splitter Pattern: The Dispatcher never builds a giant list in memory. It calculates one IP, publishes one message, moves to the next. Memory stays flat.

Contract 3: Scanner → RabbitMQ (Result Queue)

What the Scanner publishes after completing a scan. This is the existing IpState serialized format, plus job_id and labels passed through.

{
  "job_id": "JOB-0042",
  "labels": { "target_group": "professors" },
  "flags_used": {
    "check_tcp": true,
    "check_http": false
  },
  "results": {
    "192.168.1.5": {
      "metadata": {
        "resolved_from": null,
        "discovered_from": null
      },
      "ports": {
        "443": {
          "tcp_status": "open",
          "tcp_latency_ms": 12,
          "tls_certificate": {
            "valid": true,
            "expires_in_days": 90,
            "issuer": "CN=Let's Encrypt",
            "domains_discovered_sans": ["example.com"]
          },
          "http_routing_checks": {
            "192.168.1.5": {
              "status_code": 200,
              "path_checked": "/",
              "notes": "Expected string 'login' found"
            }
          }
        },
        "80": {
          "tcp_status": "closed",
          "tcp_latency_ms": null,
          "tls_certificate": null,
          "http_routing_checks": {}
        }
      }
    }
  }
}
Labels & Flags pass-through: The Scanner receives labels and flags in the Task and copies them unchanged to the Result. It never modifies them. The Result Writer uses flags_used to know which incremental timestamps to update. This is how Prometheus filtering works later without changing Scanner code.

Contract 4: API → Frontend (Results Query)

What the React frontend receives when it queries for scan results.

GET /api/jobs/JOB-0042/results?page=1

{
  "job_id": "JOB-0042",
  "status": "completed",
  "total_targets": 254,
  "completed": 254,
  "results": [
    {
      "ip": "192.168.1.5",
      "ports": {
        "443": { "tcp_status": "open", "latency_ms": 12, "tls_valid": true },
        "80":  { "tcp_status": "closed" }
      }
    },
    ...
  ],
  "page": 1,
  "total_pages": 13
}
Pagination is mandatory. A /16 CIDR scan generates 65,534 results. The Frontend must never receive all of them at once.

Final Decisions (Rules Engine)

The architectural choices finalized for the MVP database schema, job configuration, and metrics.

1. The Profile vs Trigger Pattern (Configuration Merging)

We decided against complex state-aware tri-state flags (True/False/Neutral) and overlapping crons. Instead, we decouple the Rules (Profiles) from the Execution (Jobs/Crons).

Pydantic Dictionary Merging: The Dispatcher dynamically builds the final flag set for a target by layering the profiles on top of each other. The right-most (most specific) layer wins. A Job trigger always forces its overrides across all targeted IPs.

2. Incremental Probe Timestamps

Since Jobs can run specific flags (e.g., a Job that only runs TCP checks), we cannot have a single last_scanned_at column on the target. We must track state at the probe level.

PortStateRecord (SQLite)

{
  "port": 443,
  "tcp_status": "open",
  "tcp_last_checked_at": "2026-08-26T15:00:00Z",
  "tls_valid": true,
  "tls_last_checked_at": "2026-08-26T15:00:00Z",
  "http_status_code": 200,
  "http_last_checked_at": "2026-08-25T09:00:00Z" // older!
}

When the Result Writer consumes an IpState, it inspects the flags used for that task. If check_http was false, it updates the TCP and TLS timestamps but leaves the HTTP timestamp completely untouched.

3. Prometheus Overlapping Groups

A target can belong to multiple groups. Exporting metrics with comma-separated labels (groups="professors,students") breaks PromQL aggregations.

The Join Metric Pattern (target_group_info)

# 1. The health metric contains ONLY the target identity
site_health_tcp_status{target="susy.ic.unicamp.br"} 1

# 2. The API/DB exports static "info" metrics defining membership
target_group_info{target="susy.ic.unicamp.br", group="professors"} 1
target_group_info{target="susy.ic.unicamp.br", group="department-servers"} 1

# 3. Grafana joins them dynamically
site_health_tcp_status * on(target) group_left target_group_info{group="professors"}

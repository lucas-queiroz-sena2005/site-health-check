System Architecture Guide

A comprehensive blueprint clarifying the terminology, data flows, and evolutionary phases of the Site Health Check engine.

1. Terminology Dictionary

Job (The Request)

A high-level, human-readable command. (e.g., "Scan the CIDR 192.168.1.0/24 with custom timeout flags"). It exists in the API.

Task (The Atomic Unit)

A physical JSON payload in RabbitMQ representing exactly ONE target. A single Job is expanded into thousands of Tasks.

Result (The Output)

The JSON payload generated after a Task is executed, containing status codes, latency, and custom version checks.

Label (Metadata)

Key-value tags attached to Tasks and Results (e.g., group: professors). Vital for future Prometheus querying.

2. Responsibilities Matrix

Strict separation of responsibilities prevents shallow, fragile code. Each module has a single reason to change.

Module It DOES... It DOES NOT...
API (FastAPI) Handle HTTP requests from React, write configs to SQLite, authenticate users. Do not ping websites. Do not calculate IP ranges.
Dispatcher (Splitter) Read a Job, parse CIDR blocks, query DB for "professors", and generate 1000s of JSON Tasks. Do not ping websites. Do not serve web traffic.
Scanner (Engine) Receive ONE JSON Task, ping the exact IP, check custom headers/versions, return a Result. Do not talk to SQLite. Do not parse CIDR blocks.

3. Data Contracts (JSON I/O)

Because the Scanner is entirely decoupled, we must rigorously define the exact JSON shapes it expects (Inputs) and produces (Outputs).

INPUT: The "Task" Payload

Generated by the Dispatcher, consumed by the Scanner.

{
  "job_id": "REQ-001",
  "target_ip": "192.168.1.5",
  "port": 443,
  "flags": {
    "timeout_ms": 5000,
    "verify_ssl": false,
    "check_version": true
  },
  "labels": {
    "target_group": "professors",
    "scan_type": "ad-hoc"
  }
}

OUTPUT: The "Result" Payload

Generated by the Scanner, consumed by the Database writer.

{
  "job_id": "REQ-001",
  "target_ip": "192.168.1.5",
  "status": "UP",
  "http_code": 200,
  "latency_ms": 142,
  "version_found": "nginx/1.21.0",
  "timestamp": "2026-08-25T14:55:00Z",
  "labels": {
    "target_group": "professors",
    "scan_type": "ad-hoc"
  }
}
Crucial Detail: Notice how the labels block is simply copied from the Input to the Output. The Scanner doesn't care what is in there, it just passes it through. This is the secret to making Prometheus filtering work later without changing the Scanner code!

4. Phase 1: CLI Mode (Nmap style)

Before we even turn on RabbitMQ, the Engine must work natively on your laptop. Using Hexagonal Architecture, a CLI Adapter translates terminal commands into the JSON Task contract.

5. Phase 2: MVP Microservices

We introduce the FastAPI, the Dispatcher, RabbitMQ, and SQLite. Notice that the Scanner Core did not change a single line of code. We just wrote a new Adapter (RabbitMQ Adapter) to feed it.

6. Phase 3: Full Production

We are running at massive scale. The Python Scanner is struggling, so we rewrite it in Go. We also need rich metrics, so we introduce Prometheus. Because of our strict responsibilities and JSON contracts, we do not have to touch the FastAPI, Dispatcher, or SQLite Config DB.
